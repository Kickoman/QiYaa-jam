# 09 — Джем: общая очередь для компании

_Версия 2 · 29.09.2026 · идея и архитектура, кода пока нет. v2: хостинг на имеющемся VPS, защита от ботов (§6.2), восстановление хозяина (§7), за имеющимся nginx в Docker без Caddy (§8)_

## Коротко

- **Что это.** Хозяин включает джем в QiYaa (ПК или Android). Гости сканируют QR-код и добавляют треки в общую очередь с телефона: из браузера или из своего QiYaa. Музыка звучит только у хозяина, через его аккаунт Яндекса.
- **Как устроено.** Небольшой сервер на своём VPS держит комнату: участников, очередь и правила порядка. Хозяин лишь **исполняет**: берёт у сервера следующий трек и выполняет поиск для гостей своим токеном. Токен Яндекса и звук через сервер не идут.
- **Почему логика на сервере.** Правила джема (порядок, права, лимиты) пишутся один раз, на TypeScript. На ПК (C++) и Android (Kotlin) остаётся тонкий клиент. Это та же стратегия против расхождения платформ, что и в 06/08: одна реализация плюс общая спецификация.
- **Встраивание в плеер.** Для плеера джем — ещё один источник, как волна: «дай следующий трек». Поэтому его удобно делать после задач AND-11/AND-12 (Android) и DESK-01 (ПК), где источники выносятся в отдельный слой.
- **Что проверить до кода:** принимает ли ротор волну с сидами из нескольких треков.
- **Устойчивость.** Сервер защищён слоями: фаервол, лимиты на комнаты и соединения (§6.2). Хозяин переживает обрыв связи, перезапуск приложения и сервера без потери джема (§7).

## 1. Принятые решения

| Вопрос | Решение | Следствие |
|---|---|---|
| Где звучит музыка | На одном устройстве, у хозяина | Нужен один аккаунт с подпиской — у хозяина. Синхронизировать звук между устройствами не нужно |
| Кто гости | Браузер **и** QiYaa | Веб-страница для всех (в том числе iPhone без приложения); в QiYaa — режим гостя со своим аккаунтом |
| Связь | Свой сервер-посредник | Работает из любых сетей; нужен VPS и домен |
| Хостинг | Имеющийся VPS на DigitalOcean с доменом | Участники не в РФ, поэтому ограничения доступа не касаются. Джем — отдельный поддомен и контейнер |
| Кто может быть хозяином | ПК и Android | Тонкий клиент джема пишется дважды: на C++ и на Kotlin |
| Порядок треков гостей | Переключаемый: «по кругу» или «кто первый добавил» | Порядок вычисляется из данных, а не хранится (§4.2) |
| Когда треки гостей кончились | Волна по трекам джема | Сервер выбирает сиды, хозяин запускает волну (§4.4) |
| Влияние на вкус хозяина | Не учить | В джеме не отправляются `/play-audio` и фидбек «Моей волне» за чужие треки (§4.5) |

## 2. Как это выглядит для людей

**Вечеринка у ПК.** Хозяин: меню → «Джем» → «Начать». Открывается окно в стиле скина с QR-кодом, ссылкой и списком гостей. Гость сканирует QR, вводит имя, находит трек и жмёт «+». Трек появляется в плейлисте хозяина с подписью «от Ани». Когда очередь гостей кончается, играет волна по тому, что добавляли.

**Машина с Android.** То же с телефона хозяина. QR крупно на экране или ссылка через «Поделиться» в мессенджер. Во время джема сервис воспроизведения держит соединение с сервером в фоне.

**Гость с QiYaa.** Ссылка открывает приложение (Android App Links; на ПК — вставить ссылку в «Присоединиться к джему»). Гость ищет своим аккаунтом, может добавлять из **своих** лайков и плейлистов и лайкать услышанное **себе**.

**Права по умолчанию.** Гости добавляют треки (не больше 10 ожидающих на человека), видят очередь и кто что добавил, убирают свои ещё не сыгранные треки. У хозяина есть переключатели:
- «гости могут пропускать трек» (выключено);
- «вход открыт» (включено);
- «сменить ссылку»;
- «выгнать гостя»;
- «играть следующим»;
- «удалить любой трек»;
- порядок: «по кругу» / «по добавлению».

## 3. Архитектура

### 3.1. Кто за что отвечает

```
                        ┌───────────── VPS ────────────────────────────┐
  Гость (браузер) ─HTTPS─▶ nginx (TLS) ─▶ jam-server (Docker, Node/TS)  │
       │  ▲              │   ├ отдаёт веб-приложение гостя (статика)   │
       └──┼───WSS────────┼──▶├ комнаты в памяти: участники, очередь,   │
          │              │   │  правила порядка, права, лимиты         │
  Гость (QiYaa) ──WSS────┼──▶├ пересылает поиск гостей хозяину          │
                         │   └ ничего не пишет на диск                  │
                         └───────────────▲──────────────────────────────┘
                                         │ WSS (исходящее от хозяина)
                         ┌───────────────┴──────────────────────────────┐
                         │ QiYaa хозяина (ПК или Android)                │
                         │  JamClient  — соединение, состояние комнаты  │
                         │  JamSource  — источник для плеера: «следующий»│
                         │  JamHelper  — поиск и проверка треков для     │
                         │               гостей через свой Library       │
                         │  Плеер → Яндекс Музыка (токен только здесь)   │
                         └───────────────────────────────────────────────┘
```

### 3.2. Почему правила на сервере, а не у хозяина

| Вариант | Где живут очередь и правила | Плюсы | Минусы |
|---|---|---|---|
| **Сервер главный** (выбран) | jam-server | Правила в одном месте на одном языке, тесты по спецификации. Клиенты на C++ и Kotlin тонкие. Комната переживает короткий обрыв связи у хозяина | Без сервера джема нет (это уже принято выбором «свой посредник») |
| Хозяин главный, сервер — ретранслятор | QiYaa хозяина | Сервер совсем простой | Логику порядка, прав и лимитов пришлось бы писать дважды, на C++ и на Kotlin, и они бы разошлись |
| Без сервера, через плейлист Яндекса | Совместный плейлист | Ничего не хостить | Совместные плейлисты в API не подтверждены: источники противоречат друг другу, по [отзывам](https://yandexmusic.userecho.ru/communities/45/topics/8252-sovmestnyie-plejlistyi) функцию убирали. Порядка «по кругу» и прав не сделать |

**Хозяин всё равно нужен для трёх вещей, которые без токена Яндекса невозможны:** звук, поиск для веб-гостей и проверка доступности трека в регионе и подписке хозяина. Сервер эти запросы только пересылает.

### 3.3. Джем внутри плеера

Джем — источник для слоя, который выносится в AND-11 (Android, `queue/`) и DESK-01 (ПК, `core/`), по образцу волны:

- `JamSource.next()` сначала берёт первый трек из очереди джема, **уже лежащей в локальной копии состояния**, — без запроса к серверу. Поэтому работают предзагрузка и стыковка без пауз. Если очередь пуста — трек волны джема (§4.4).
- Трек начал играть → хозяин сообщает `started(itemId)`. Сервер переносит его в историю и пересчитывает порядок.
- Очередь изменилась и первый трек стал другим → плеер отменяет предзагрузку, как при любом изменении очереди.
- У источника есть флаг «не учитывать прослушивание» (§4.5), его проверяет трекер прослушивания из AND-13.
- Плейлист хозяина во время джема показывает: текущий трек → очередь джема (с именами гостей) → «дальше волна джема».

## 4. Модель и правила

### 4.1. Данные комнаты

```
Room        id, hostSecret, joinSecret, settings, participants[], queue[], history[], nowPlaying, version
Settings    order: ROUND_ROBIN | FIFO, guestsCanSkip, joinOpen, maxPendingPerGuest (10), maxGuests (30)
Participant id (случайный, хранится у гостя), name, kind: HOST | WEB | QIYAA, joinedAt, lastServedAt?, kicked
QueueItem   itemId, track {id, title, artists[], durationMs, coverUri}, addedBy, addedAt, pinned
NowPlaying  source: ITEM(itemId) | WAVE, track, positionMs, paused, reportedAt (время сервера)
```

`version` растёт на каждое изменение. Клиенты получают полный снимок и игнорируют снимки со старой версией. Очередь при этом короткая: несколько десятков треков, это единицы килобайт.

### 4.2. Порядок и его переключение

Порядок **вычисляется** из данных при каждом изменении, а не хранится:

```
очередь = [закреплённые хозяином («играть следующим»), в порядке закрепления]
        + политика(остальные)
```

- **FIFO:** по `addedAt`; при равенстве по `itemId`.
- **По кругу:**
  1. У каждого участника свои треки идут по `addedAt`.
  2. Участников с ожидающими треками упорядочить: сначала тех, чей трек дольше всего не играл (`lastServedAt`, «ещё ни разу» — впереди). При равенстве — по самому раннему ожидающему треку, потом по `id`.
  3. Круг 1 — по одному треку от каждого в этом порядке, круг 2 — так же, и так далее.

  Отсчёт идёт от того, кто **давно звучал**, а не от того, кто давно добавил. Поэтому пришедший позже гость попадает в ближайший круг, а не в конец часовой очереди.
- **Переключение режима** сразу пересчитывает незакреплённую часть и рассылает новый снимок. Текущий трек и закреплённые не двигаются.
- Хозяин тоже участник: его треки идут в общий круг. «Играть следующим» — это закрепление, оно обходит политику.
- **Повторы:** трек, который уже ждёт в очереди, повторно не добавляется (гостю приходит «уже в очереди от Бори»). После проигрывания его снова можно добавить.

Функция порядка — чистая: (элементы, история, режим) → порядок. Её эталонные сценарии лежат в `spec/jam/ordering/*.json` (§8), по ним тестируется сервер.

### 4.3. Права и лимиты (на сервере)

| Действие | Гость | Хозяин |
|---|---|---|
| Добавить трек | да, до `maxPendingPerGuest` ожидающих, не чаще 10 в минуту | да, без лимита |
| Убрать трек | только свой и ещё не сыгранный | любой |
| Играть следующим | нет | да |
| Пропустить текущий | если `guestsCanSkip` | да (своей кнопкой в плеере) |
| Поиск (для веб-гостей) | не чаще 20 в минуту | — |
| Выгнать, закрыть вход, сменить ссылку, сменить порядок, закончить | нет | да |

Лимит на поиск защищает **аккаунт хозяина**: все поиски веб-гостей идут его токеном.

### 4.4. Когда очередь гостей пуста: волна джема

- Сервер держит список сидов: последние ~5 треков джема (сыгранных и добавленных) в виде `track:<id>`, дополненные исполнителями этих треков.
- Очередь опустела → в снимке `fallback = {seeds, seedsVersion}` → `JamSource` запускает волну (`Library.startWave(seeds)`) и берёт треки из неё.
- Гость добавил трек, пока играет волна → он заиграет **после текущего** трека волны, а не оборвёт его.
- Сиды изменились за время, пока играли треки гостей → при следующем возврате к волне стартует новая сессия. Если не изменились — продолжается старая.
- Треки волны не попадают в очередь джема, гости видят «сейчас: волна джема».
- **Проверить прототипом:** принимает ли `/rotor/session/new` несколько сидов `track:…`/`artist:…` в одном запросе. Десктоп уже передаёт список сидов для колеса волн, но с чужими видами сидов это не проверялось. Если не принимает — сид из одного последнего трека.

### 4.5. Что уходит в Яндекс от имени хозяина

- Треки из очереди джема: **ни `/play-audio`, ни фидбека «Моей волне»**. История и рекомендации хозяина не меняются.
- Волна джема: фидбек идёт в её собственную сессию ротора, чтобы она подстраивалась под компанию. **Риск:** неизвестно, влияет ли фидбек в такой сессии на общий профиль хозяина. Если есть сомнение — выключить и его (одна настройка в `JamSource`).
- Лайк хозяина (его кнопкой) — осознанное действие, уходит как обычно. Гость из QiYaa лайкает в **свой** аккаунт. Веб-гость лайкать не может.

## 5. Протокол (набросок v1)

JSON-сообщения поверх WebSocket, у каждого есть `type`. Первое сообщение клиента — `hello` с `protocol: 1`. Сервер отвечает `welcome` или `error{code: "update-required"}`.

**Хозяин → сервер**

| Сообщение | Смысл |
|---|---|
| `create{name, settings}` | Новая комната → `created{roomId, hostSecret, joinSecret, joinUrl}`. Сверх лимитов на комнаты (§6.2) — отказ |
| `resume{roomId, hostSecret, snapshot?, outbox[]}` | Переподключение (§7). `snapshot` нужен, только если сервер комнату забыл. `outbox` — события, накопленные без связи |
| `nowPlaying{source, itemId?, track, positionMs, paused}` | При смене трека, паузе, перемотке и раз в 10 с |
| `started{itemId}` | Трек из очереди начал звучать → он уходит в историю. Повтор с тем же `itemId` ничего не меняет |
| `searchResult{requestId, tracks[] \| error}` | Ответ на поиск веб-гостя |
| `validated{requestId, results[]}` | Проверка треков, добавленных гостем из QiYaa: доступен ли трек хозяину |
| `pin`, `remove`, `kick`, `settings`, `rotateLink`, `end` | Действия хозяина |

**Гость → сервер**

| Сообщение | Смысл |
|---|---|
| `join{roomId, joinSecret, participantId, name, kind}` | Вход. `participantId` генерирует и хранит сам гость, поэтому переподключение сохраняет его «я» |
| `search{requestId, text}` | Только веб-гость. Пересылается хозяину, ответ возвращается тому же гостю |
| `add{track}` | Веб-гость — трек из результатов поиска. Гость из QiYaa — трек из своего аккаунта, хозяин его проверяет |
| `remove{itemId}`, `skip{itemId}` | По правам из §4.3. `skip` указывает текущий трек, чтобы два быстрых нажатия не пропустили два трека |

**Сервер → все**

| Сообщение | Смысл |
|---|---|
| `state{version, room}` | Полный снимок после каждого изменения (у гостя — без секретов и чужих `participantId`) |
| `rejected{requestId?, reason}` | Лимит, повтор, нет прав, трек недоступен хозяину, выгнан |
| `command{skip}` | Только хозяину: гость пропустил трек (если разрешено) |
| `hostOffline` / `ended` | Хозяин пропал / джем закончен |

**Ключевые сценарии**

```
Добавление из браузера:
  гость ─search→ сервер ─search→ хозяин (Library.search своим токеном)
  гость ←searchResult─ сервер ←searchResult─ хозяин
  гость ─add{track}→ сервер: права, лимит, повтор → очередь → state всем

Смена трека:
  плеер хозяина: JamSource.next() = первый трек очереди из локального state
  хозяин ─started{itemId}→ сервер: в историю, lastServedAt, пересчёт → state всем
```

Обрыв связи и перезапуски — в §7.

Сообщения фиксируются JSON Schema в `spec/jam/protocol/` с примерами. Из схемы генерируются типы TypeScript, а парсеры на C++ и Kotlin проверяются на тех же примерах.

## 6. Безопасность

### 6.1. Кто что может

- **Ссылка:** `https://<домен>/j/<roomId>#<joinSecret>`. Секрет (128 бит) стоит во фрагменте после `#`, поэтому не попадает в HTTP-запрос и в логи сервера: веб-приложение само достаёт его и отправляет в `join`. Короткого кода «для ввода руками» в v1 нет: 6 символов слишком легко перебрать.
- **Создавать комнаты** может любое приложение QiYaa; сколько — ограничивают лимиты (§6.2).
- **Управлять комнатой** может только хозяин: он подтверждает право `hostSecret` (256 бит), который хранит у себя до конца джема.
- **Токен Яндекса** не покидает устройство хозяина. Гостям уходят только метаданные треков. Обложки гости грузят напрямую с `avatars.yandex.net`: это публичные ссылки без токена.
- **Выгнанный гость** блокируется по `participantId`. Это защита от случайных людей, а не от упорного злоумышленника. Против упорного есть «сменить ссылку» и «закрыть вход».
- **Приватность:** комнаты живут в памяти, а на диск попадают только на время перезапуска сервера (§7.3). В логах нет названий треков и имён, только счётчики и причины отказов.

### 6.2. Боты и спам

> **2026-10-01: ключей хозяина больше нет.** Сначала создавать комнаты могли только владельцы ключа,
> который выдаёт владелец сервера. На практике это значило, что каждому, кто хочет начать джем,
> нужно получить ключ и вставить его в настройки, и для приложения, которым пользуются другие, это
> неприемлемо. Теперь комнату создаёт любое приложение, а слой «ключ хозяина» заменён лимитами на
> комнаты одного IP. Чем платим: кто-то с многих адресов может занять все 20 комнат, и честные
> хозяева получат `server-full`; а гость, знающий `roomId`, может занять id комнаты, истёкшей без
> хозяина, раньше, чем хозяин её поднимет, — тогда джем хозяина закончится (HOST-24). Для нашего
> масштаба это приемлемо; если станет проблемой, лимиты можно ужесточить.

Одного незнания протокола мало. Любой, кто откроет веб-страницу гостя, увидит протокол в её JavaScript. Поэтому защита устроена слоями — от «сервер вообще не отвечает» до «отвечает, но недорого».

| Слой | Что делает | От чего защищает |
|---|---|---|
| **Облачный фаервол DigitalOcean** | Снаружи открыты только 80 и 443, SSH — только по ключу (и, по возможности, только со своих адресов) | Перебор SSH, случайные сервисы на других портах |
| **nginx** (уже стоит на VPS) | TLS и проксирование на контейнер. Сам jam-server отдаёт только статику и `/ws`, на всё остальное — 404. Лимит размера запроса (`client_max_body_size`) | Сканеры, которые ищут `/wp-login.php` и `/.env`: получают пустой 404 и уходят |
| **Лимиты на комнаты** | Не больше 2 живых комнат и 5 новых в час с одного IP; подъём комнаты из снимка считается новой комнатой | Чужой, кто прочитал протокол, не займёт сервер своими комнатами с одного адреса |
| **Рукопожатие** | После подключения за 5 с должно прийти `hello` с правильной версией протокола, иначе соединение закрывается. Для браузеров проверяется `Origin` — только наш домен | Висящие пустые соединения, чужие сайты, которые открывают сокеты из браузеров своих посетителей |
| **Строгий разбор** | Сообщение больше 16 КБ, не по схеме или неизвестного типа → соединение закрывается. Три таких закрытия с одного IP → бан на 10 мин | Мусор и фаззинг |
| **Лимиты на IP** | IP клиента берётся из `X-Real-IP`, который ставит nginx; самому заголовку сервер верит, только если соединение пришло от nginx. Не больше 20 соединений одновременно и 30 новых в минуту. Неудачные `join` (неверный секрет) — не больше 10 в минуту | Перебор ссылок (128 бит и так не перебрать, но лишний раз сервер не нагружаем), потоп подключений |
| **Лимиты в комнате** | §4.3: добавления, поиски, до 30 гостей | Злоупотребление внутри комнаты. В том числе защищает аккаунт хозяина от лишних поисков |
| **Глобальные потолки** | Не больше 20 комнат одновременно, общий объём памяти на комнаты ограничен | Даже если комнаты займут с многих адресов, сервер не падает, а отказывает |

Для нашего масштаба этого с запасом хватает. Капча, аккаунты и внешняя защита от DDoS не нужны. Если однажды придёт настоящий DDoS, ни одна из мер уровня приложения от него не спасёт — это уже задача провайдера.

## 7. Если хозяин потерял связь

Коротко: да, хозяин защищён, и восстановиться можно в любой момент до конца джема, в том числе после перезапуска приложения или сервера.

### 7.1. Короткий обрыв: тоннель, лифт, переключение Wi-Fi

- **Музыка не останавливается.** `JamSource` играет по своей локальной копии очереди: текущий трек, дальше те, что уже известны. Если известные треки кончились, запускается волна джема по сохранённым сидам. Ей нужен только интернет до Яндекса, сервер джема не нужен.
- **События не теряются.** Пока связи нет, `started{itemId}` и прочее складываются в `outbox`. При переподключении они уходят вместе с `resume`, и сервер применяет их по `itemId` без дублей.
- **Действия хозяина** (удалить, закрепить, настройки) без связи недоступны. Кнопки неактивны, в окне джема видно «нет связи с сервером». Так не нужно разрешать конфликты с тем, что гости сделали за это время.
- **Гости продолжают добавлять.** Сервер главный и принимает добавления без хозяина. Гости видят «хозяин не в сети». Поиск для веб-гостей в это время недоступен: его делает хозяин.
- **Переподключение автоматическое:** через 1, 2, 4… 30 с, и сразу при появлении сети.

### 7.2. Долгий обрыв, закрытое приложение, перезагрузка телефона

- Пока джем не закончен, хозяин хранит на диске `roomId`, `hostSecret`, последний снимок комнаты и `outbox`.
- При запуске QiYaa предлагает «Продолжить джем?». Согласие → `resume`. Отказ → `end`, и гости видят «джем закончен».
- Сервер держит комнату без хозяина **1 час** (настраивается; 15 мин из первой версии мало для поездки). После этого комната закрывается, но хозяин может её восстановить (§7.3).

### 7.3. Сервер перезапустили или комната истекла

- **Плановый перезапуск (деплой).** `docker stop` присылает `SIGTERM`, сервер сохраняет все комнаты в файл на подключённом томе и при старте загружает их обратно (`stop_grace_period` в compose — с запасом, например 30 с). Клиенты переподключаются сами, никто ничего не замечает.
- **Аварийный перезапуск или истёкшая комната.** Хозяин присылает `resume{snapshot}`, и сервер восстанавливает комнату из этого снимка **с теми же `roomId` и `joinSecret`**. Ссылки гостей продолжают работать, гости переподключаются со своими `participantId`. То, что гости добавили после последнего снимка хозяина, теряется. Это единственная потеря, и только при аварии.
- **Если комната на сервере жива**, главнее сервер: снимок хозяина игнорируется, применяется только `outbox`.
- **Восстановить комнату из снимка** можно только с `hostSecret` этой комнаты, и это считается созданием новой комнаты для лимитов §6.2.

### 7.4. Бонус того же механизма: передать джем на другое устройство

`resume` с другого устройства — это смена хозяина: начал в машине с телефона, дома перенёс на ПК к колонкам. Для этого нужно передать `roomId` и `hostSecret` — QR-кодом со старого устройства на новое. Старое соединение получает `replaced` и перестаёт играть. В v1 не делаем, но протокол к этому готов.

## 8. Где живёт код

| Что | Где | Язык |
|---|---|---|
| Протокол (JSON Schema + примеры), сценарии порядка, прав и восстановления | `spec/jam/` — в общем репозитории спецификации из SPEC-01 | JSON / Markdown |
| Сервер, веб-приложение гостя, деплой | новый репозиторий `Kickoman/QiYaa-jam`: `server/`, `web/`, `deploy/`; `spec/` подмодулем | TypeScript |
| Хозяин и гость на ПК | `QiYaa`: модуль `jam/` (JamClient, JamSource, JamHelper), окно джема в стиле скина, пункт меню | C++/Qt: Qt WebSockets (LGPLv3, как остальной Qt; пакет `qt6-websockets-dev`), QR — [qrcodegen](https://github.com/nayuki/QR-Code-generator) (MIT) |
| Хозяин и гость на Android | `QiYaa-android`: пакет `jam/`, экран джема, App Links на домен | Kotlin: WebSocket из OkHttp, QR — qrcodegen (Java-версия) |

**Сервер.** Node 22 + TypeScript: HTTP для статики, `ws` для WebSocket. Логика комнаты — чистый редьюсер `(state, event) → (state, effects)`, тестируется сценариями из `spec/jam`. Один процесс, одна маленькая машина (1 vCPU / 512 МБ с запасом). Один Docker-контейнер (`jam-server` отдаёт и статику веб-гостя, и WebSocket), том для файла комнат при перезапуске. GitHub Actions: тесты, образ в GHCR, деплой по SSH (`docker compose pull && up -d`). Альтернатива — Go (один статический бинарник, меньше памяти). Но тогда сервер и веб-клиент будут на разных языках и не смогут делить типы протокола; для проекта одного человека с агентами это важнее.

**Веб-приложение гостя.** Лёгкое SPA на Preact или Svelte, цель — < 100 КБ, потому что грузят с мобильного интернета. Дизайн — токены мобильной дизайн-системы Android-версии (IBM Plex, LED-акцент). Интерфейс на русском и английском. Экраны: имя → «сейчас играет» + очередь → поиск.

**Хостинг.** Уже есть VPS на DigitalOcean с доменом и nginx перед Docker-контейнерами. Джем встаёт в тот же ряд: поддомен `jam.<домен>`, свой `server`-блок в nginx, сертификат тем же способом, что у остальных сервисов. Контейнер слушает только `127.0.0.1` (или общую docker-сеть с nginx), наружу порт не публикуется.

```nginx
server {
    listen 443 ssl http2;
    server_name jam.example.org;
    # ssl_certificate … — как у остальных сервисов

    client_max_body_size 64k;

    location /ws {
        proxy_pass http://127.0.0.1:8090;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_read_timeout 1h;   # по умолчанию 60 с: nginx рвал бы тихие сокеты
        proxy_send_timeout 1h;
    }

    location / {
        proxy_pass http://127.0.0.1:8090;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

**Ловушки:**
- без `Upgrade`/`Connection` WebSocket не поднимется;
- без длинного `proxy_read_timeout` nginx закрывает сокет после 60 с тишины. Сервер вдобавок сам шлёт ping каждые 25 с, чтобы соединение не считалось простаивающим;
- если перед nginx есть ещё что-то (балансировщик DigitalOcean, Cloudflare-прокси), `X-Real-IP` нужно брать из `real_ip_header` этого звена.

## 10. Риски и открытые вопросы

| # | Что | Как снимаем |
|---|---|---|
| 1 | Ротор может не принять волну из нескольких сидов-треков | Разведка S1; запасной вариант — волна по последнему треку |
| 2 | Поиски гостей идут токеном хозяина | Принято: гостей немного, ищут нечасто. Лимиты §4.3 остаются страховкой |
| 3 | Фидбек волны джема может влиять на общий профиль хозяина | Настройка «фидбек волне джема» (выключается одной строкой) |
| 4 | Android: фоновое соединение, пока музыка на паузе | Сервис воспроизведения остаётся на переднем плане всё время джема (уведомление «Идёт джем») |
| 5 | Трек, добавленный гостем из QiYaa, недоступен хозяину (регион или подписка) | Хозяин проверяет через `/tracks` (`validated`), гостю приходит `rejected` с причиной |
| 6 | Аварийный перезапуск сервера теряет то, что гости добавили после последнего снимка хозяина | Принято: снимок у хозяина обновляется при каждом `state`, окно потери — секунды |
