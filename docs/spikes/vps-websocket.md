# Разведка: nginx → контейнер → WebSocket на VPS

Kickoman/QiYaa-jam#2 · 30.09.2026 · эхо-сервер [deploy/echo/](../../deploy/echo/)

**Вопрос.** Проходит ли долгий WebSocket через имеющийся nginx и доходит ли до контейнера настоящий
IP клиента из `X-Real-IP`.

**Вывод.** Проходит, IP доходит. Но контейнер видит nginx не как `127.0.0.1`, а как шлюз своей
docker-сети. Поэтому значение по умолчанию `TRUSTED_PROXY=127.0.0.1` из Kickoman/QiYaa-jam#8 в
контейнере не работает: подсеть compose нужно закрепить, а доверять её шлюзу.

## Как устроено

- Эхо-сервер (Node 22 + `ws`) в контейнере, опубликован только на `127.0.0.1:8090`. Отдаёт
  тестовую страницу `/`, `/healthz` и WebSocket `/ws`. Раз в 25 с шлёт ping, закрывает соединение
  через 60 с без pong. Пишет в лог JSON: адрес соседа (`peer`), заголовок `X-Real-IP`, итоговый IP,
  длительность и код закрытия.
- nginx: отдельный `server`-блок по образцу 09 §8 ([deploy/nginx.conf.example](../../deploy/nginx.conf.example)).
  Поддомена пока нет, поэтому временно это отдельный порт `8443` на основном домене с его
  сертификатом, порт открыт в ufw.

## Проверки

| Что | Как | Результат |
|---|---|---|
| Страница, `/healthz`, чужой путь | `curl` снаружи | 200, 200 `ok`, 404 |
| WSS через nginx | клиент Python `websockets`: `hello` → эхо | работает, эхо за 27 мс |
| `X-Real-IP` до контейнера | запрос с ноутбука в обход VPN, страница и WebSocket | в логе внешний адрес ноутбука |
| Кто сосед у контейнера | лог `peer` | шлюз docker-сети compose, не `127.0.0.1` (см. ниже) |
| Тишина дольше 60 с | WebSocket без сообщений 150 с, потом эхо | соединение живо, 5 ping/pong, эхо ответило |
| Телефон (Firefox, Android) | открыл страницу | соединение открылось; закрыто через 19 с с кодом 1006, причина неизвестна |
| 30 мин тишины с телефона | — | **не проверено**: владелец отложил |
| Переключение Wi-Fi ↔ мобильная сеть | — | **не проверено** |
| Мобильный интернет без VPN | — | **не проверено** |

## Что узнали

1. **Доверенный прокси — шлюз docker-сети.** Контейнер в сети bridge, опубликованный на
   `127.0.0.1:PORT`, получает соединения nginx от шлюза своей сети (например, `172.24.0.1`), а не
   от `127.0.0.1`. Адрес шлюза меняется вместе с сетью compose. Решение, проверенное здесь:
   закрепить подсеть в `compose.yml` и передать её шлюз в `TRUSTED_PROXY`:

   ```yaml
   networks:
     default:
       ipam:
         config:
           - subnet: 172.30.90.0/24
             gateway: 172.30.90.1
   ```

   Другой вариант — `network_mode: host` и сервер на `127.0.0.1`, тогда подходит значение по
   умолчанию. Но так контейнер теряет свою сеть. Для Kickoman/QiYaa-jam#8 и #12 предлагается первый вариант.
2. **Клиенты за VPN владельца выглядят одним адресом.** Устройства, которые выходят в интернет через
   WireGuard на этом же VPS, приходят в nginx с адреса контейнера WireGuard, а не со своих. Для
   джема это значит, что лимиты «на IP» (10 A4) делят все такие гости вместе. Для компании из
   нескольких человек запаса хватает: 20 соединений, 30 новых в минуту.
3. **`proxy_read_timeout 1h` не обязателен, но безвреден.** Ping сервера каждые 25 с и так держит
   соединение живым дольше 60-секундного тайм-аута nginx. Настройка остаётся страховкой на случай,
   если ping сломается.
4. **Сертификат.** Сертификат основного домена поддомен `jam.` не покрывает. Для поддомена нужен
   свой сертификат (`certbot --nginx -d jam.<домен>`), как у остальных поддоменов на этом VPS.
